# CS-230-Operating-Systems-Journal: The Gaming Room
This repository contains the software design document and my reflections for the Gaming Room Project.
## Client and Software Requirements
The client for this project was the Gaming Room. They wanted a web based version of their existing Android game, Draw It or Lose It. The software needs to be able to support multiple teams with multiple players on a team. One of the main requirements was to ensure that only one game instance of a game, team or player could exist within memory at a time. Secondly, the application required us to transition from a mobile only environment to a responsive web application, handling the new restraints such as keyboard and mouse support, various monitor resolutions and memory limits introduced by the browsers.
## Strength in Documentation
While developing the design document, I feel like I did particularly well with evaluating the various operating platforms and devising comprehensive recommendations. By providing a thorough evaluation of the server side, client side and development tools that are available on Mac, Linux, Windows and Mobile devices, I was able to plainly and strongly advise that the Linux based server architecture prioritizing a mobile first web interface was the best plan moving forward. The memory management and distributed systems recommendation were also highly thought out and tried to tailor to the needs of a real-time drawing game.
## Value in the Design Process
While working through the design document, the Domain model and the UML diagram were especially helpful for visualizing the code structure before writing it. Defining the GameService class as a singleton and mapping out how Game, Team and Player inherited from Entity provided a clear blueprint, eliminating unnecessary guesswork during development since the relationships and methods were clearly established.
## Areas for Revision
If I were to go back and revise one part of this design document I would probably restructure the Design Constraint section. Currently, the constraints talking about RAM limitations, input method adjustment and screen resolution scaling are grouped into a singular paragraph. In order to improve the readability for the development team, I would include specific subsections such as Hardware Limitations, UI/UX Adaptions and Network Constraints and use lists rather than long form paragraphs. This format would make it easier to track individual constraints and that each issue was addressed successfully when used alongside the Agile development process.
## Implementing and Interpreting User Needs
Interpreting the needs of the user means looking at the limitations introduced by moving from native android app to a web browser. I addressed these needs by adjusting the design constraints directly by planning for assets to be downloaded dynamically to save precious RAM resources, modifying the touch controls to now respond to keyboard and mouse inputs and ensure that the program adapts to various screen resolutions presented by different types of monitors. Considering the needs of the users is instrumental because a poor user experience, such as the browser refreshing accidentally or UI that doesn't fit on the screen would drive players away regardless of numerous other flawless parts of the application.
## Approach to Software Design and Future Ideas
My approach to designing this software was heavily based in the concepts of Object Oriented Programming (OOP) principles and using established design patterns. By utilizing encapsulation, inheritance and the singleton pattern I could ensure the integrity of application data and manage the software states efficiently. In the future, if I were to analyze or design a similar program I would use more flow diagrams and sequence diagrams in order to map out exactly how the data is traveling between the client and the server during actual usage. I would also incorporate the ideas of Agile for testing the user interface and user experience early with play testers to ensure that the new variant of the application felt natural and had a good flow.
